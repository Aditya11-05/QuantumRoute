# Limitations

Documented explicitly and honestly, per the project's own "do not hide
limitations" requirement.

## 1. Synthetic traffic data in demo mode

All traffic scenarios (`app/simulation/traffic.py`) are generated by a
deterministic, seeded simulator, not a live traffic feed. This was a
deliberate, necessary choice for an offline-capable SIH demo, but it
means congestion numbers reflect a simulation, not reality. See the
`disclaimer` field returned by every relevant API response.

## 2. Limited geographic region

The demo graph is either a small synthetic 9×9 grid (~80 nodes) or, in
live mode, whatever OSMnx downloads for a single named region (default:
Kashipur, Uttarakhand). The system has not been tested at city scale or
beyond.

## 3. No live network access verified in this development environment

This codebase's live-OSM code path (`graph_loader.py::_try_download_osm`)
uses OSMnx/Overpass and was **written but could not be executed** in
the sandboxed environment used to build this project, which only
allows egress to package registries (PyPI, npm, GitHub) — not
`nominatim.openstreetmap.org` or Overpass. When you run this on your
own laptop with normal internet access, `PROJECT_MODE=live` should
work; this has not been independently verified by the assistant that
wrote this code, only reasoned about from the OSMnx API contract.
**Test this yourself before relying on it for your demo**, and keep
`PROJECT_MODE=demo` as your fallback.

## 4. Classical execution of "quantum-inspired" optimization

No quantum hardware is used anywhere. Simulated annealing runs on
ordinary CPU. See `docs/optimization.md` for the full honesty
statement. If you are asked "is this really quantum," the correct
answer is no.

## 5. QUBO scalability

The QUBO here has one variable per *candidate route* (typically 5), not
per road segment. This keeps it tractable but means QuantumRoute
currently cannot express finer-grained combinatorial constraints (e.g.
"never use more than 2 primary-road segments") without extending the
candidate representation or the QUBO itself. A full edge-level QUBO for
a real city would have far too many variables for classical simulated
annealing (or, honestly, most current quantum annealers) to handle
without significant problem decomposition.

## 6. Nearest-node lookup is a linear scan

`app/routing/node_utils.py::nearest_node` scans every node — fine for
our demo graph (tens to low thousands of nodes) but would need a
KD-tree or similar spatial index (e.g. `osmnx.distance.nearest_nodes`,
which uses `scipy.spatial.cKDTree` internally) for a full-city graph.

## 7. Dependence on OSM data quality (in live mode)

Real OpenStreetMap data has inconsistent tagging: missing `maxspeed`,
missing `lanes`, inconsistent `highway` classification. The code
defensively falls back to reasonable defaults (see
`cost.py::compute_edge_cost`'s `.get(..., default)` calls) but has not
been validated against real OSM data for the target region, since that
data could not be downloaded in this environment (see limitation #3).

## 8. Simplified fuel/energy estimation

`_fuel_proxy()` in `cost.py` is a documented **proxy**: a simple
function of congestion level and road type, not a calibrated
vehicle-specific fuel consumption model. It captures the qualitative
fact that stop-start driving burns more fuel per meter than free-flow
driving, but should not be presented as a quantitatively accurate fuel
estimate.

## 9. Limited real-world traffic integration

There is no integration with a live traffic API (Google Maps traffic
layer, TomTom, HERE, etc.) — this was an explicit scope decision (see
problem statement §8: "use synthetic traffic data so the application
works without requiring a proprietary live traffic API"), not an
oversight.

## 10. Single-vehicle, single-request optimization only

The current QUBO formulation optimizes one route for one vehicle per
request. It does not model interactions between multiple simultaneous
vehicles (shared road capacity, platooning, fleet-wide load balancing)
— this is exactly the kind of extension where a genuinely larger QUBO
with inter-vehicle constraint terms would provide real algorithmic
value over classical per-vehicle shortest-path search (see
`docs/optimization.md`'s "what does QuantumRoute actually contribute"
section for why this matters for the innovation narrative).

## 11. Frontend not tested in a real browser by the assistant

The frontend was verified to type-check, build (`npm run build`
succeeds), and serve (`npm run preview` responds with HTTP 200), and
its API calls were verified to match the backend's real response
shapes. However, no headless-browser screenshot tool was available in
the development environment, so the actual rendered visual design
(colors, layout, map rendering) has not been visually inspected by the
assistant — please do a manual visual check with `npm run dev`.
